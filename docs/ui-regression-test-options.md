# UI 層の回帰テストをどうするか（判断待ち・Day108 起票）

**これはユーザー（＝えぐしゅぎ）の判断が必要な提案書**です。devDeps の追加は行っていません。
Day106〜108 で「無音の失敗」を潰した結果、**静的ガードでは守れない契約**が残ったため、選択肢と工数をまとめます。

## 1. いま守れていないもの

Day106〜108 で入れた修正の中身は、ほぼ「**失敗したときに何が画面に出るか**」です。
`test/lib/silent-failure-coverage.test.ts` は**書き方**（catch の有無・生 message の露出・購読エラーの扱い）を
静的に検査しますが、次は検査できません:

| 守りたい契約 | 例 | 静的ガードで検出できるか |
|---|---|---|
| 失敗時にダイアログ/フォームを閉じない（入力を捨てない） | 顧客の保存が失敗 → ダイアログは開いたまま・入力は残る | ✕ |
| 失敗表示が**実際に見える場所**に出る | 体験入店エディタは fixed オーバーレイ。本文側のバナーは裏に隠れる（Day106-PM の実害） | ✕ |
| 成功時だけ入力をクリアする | 送迎リクエスト（Day107 の実バグ。await せず即クリア＝入力は消えたのに未登録） | △（`await onAdd` の有無なら可・意味は見ていない） |
| 楽観更新の巻き戻し | 予定の削除が失敗 → 一覧から消さない（Day107） | ✕ |
| ロール取得失敗を「権限なし」と誤表示しない | 通信断で「オーナー専用です」と出さない（Day108） | ✕（純ロジックは `shop-role-state.test.ts` で固定済み） |

つまり **「壊れたときの見え方」だけがテストの空白地帯**です。実害はすべてここで起きています。

## 2. 選択肢

### A. `@testing-library/react` + jsdom を導入（推奨）

- 追加 devDeps: `@testing-library/react` / `@testing-library/jest-dom`（任意） / `jsdom`
- vitest 設定: 現在 `environment: 'node'`。**プロジェクト分割**が要る
  （`test/lib/**` は node のまま、`test/ui/**` だけ jsdom）。1ファイルの設定変更で済む。
- 書けるテスト例（今日までの実害をそのまま固定できる）:
  - 保存が reject → ダイアログが**閉じない**・入力値が残る・`role="alert"` に案内文が出る
  - オーバーレイ内の操作 → **モーダルの中**に `role="alert"` がある（本文側ではない）
  - 送迎フォーム: `onAdd` が失敗文言を返す → 入力が**残る**
  - ロール取得失敗 → 「オーナー専用」ではなく「権限を確認できませんでした」
- コスト: 導入 1〜2h、以後1テスト 10〜20分。Firebase は既存テストと同じく `vi.mock` で差し替え。
- リスク: 低。既存の 100 ファイル・990 テスト（node 環境）は影響を受けない。

### B. Playwright（実ブラウザ E2E）

- MCP 経由の Playwright は運用で使っているが、**リポには未導入**（`@playwright/test` が必要）。
- 実 Firebase / エミュレータと認証が要るため、CI で回すには準備が大きい（1日以上）。
- 「本当に見えるか」を最も忠実に検証できるが、**今日の目的（失敗時の表示）には過剰**。
- 将来「導入E2E（招待→打刻→POS→給与）」を自動化したくなった時の選択肢。

### C. 現状維持（静的ガードのみ）

- 追加コストゼロ。ただし上表の空白地帯は**レビュー頼み**のまま。
- Day106-PM で実際に「修正したのにオーバーレイの裏で見えない」を踏んだため、
  同じ取りこぼしは再発しうる。

## 3. 推奨

**A（testing-library + jsdom）**。理由は、今週の実害がすべて「失敗時の見え方」に集中しており、
A なら**その1点だけを低コストで固定**できるため。B は目的に対して重く、C は再発を止められない。

## 4. 判断してほしいこと

2. 進める場合、最初に固定するのはどれか（推奨: 顧客ダイアログ・送迎フォーム・ロールゲートの3本）。
3. B（Playwright）は「導入E2E の自動化」を始めるときに別途検討、で良いか。
