# 広告配信の実装制約（2026-08-21 記録・**未実装**）

戦略転換により、最終的なマネタイズは「個人営業で獲得した企業からの広告」になった。
全員の売上を管理しているからこそできる「利用者に合った広告の出し分け」が差別化になる。

**このドキュメントは実装ではなく制約の記録である。** 広告配信のコードはまだ 1 行も無い。
将来実装するとき、ここに書いた線を越えないこと。法的な裏付けは
`/privacy`（正本は `src/lib/legal/documents.ts`）の利用目的・第三者提供の節にある。

なぜ先に書くか: 広告の実装は「セグメントを作る」「配信する」「効果を測る」の順に進み、
**最初の一歩でデータの持ち方が決まってしまう**。個票を持つ設計にしてから直すのは、
すでに配ったデータを回収できない以上ほぼ不可能になる。

---

## 制約（コードで守る）

| # | 制約 | 内容 | 破ったときに起きること |
|---|---|---|---|
| 1 | **個票は絶対に外に出さない** | 広告主に渡すのはセグメントのみ。個人の売上額・収入額を返す API を作らない | プライバシーポリシーに明記した約束（「個々の利用者の売上金額、収入額その他の個別データ（個票）を提供することはありません」）の違反。撤回不能 |
| 2 | **最小セグメントサイズ（k-匿名性）** | 該当者が N 人未満のセグメントは広告主に開示しない。**N は未確定（ユーザー判断待ち・推奨 100）** | 「渋谷・月商 500 万円以上」が 1 人しか居なければ、セグメントは個票と同義になる |
| 3 | **セグメントは範囲で持つ** | 「月商 87 万円」ではなく「月商 50〜100 万円帯」として保持・利用する | 生値を保持すると、いつか誰かがそれを直接使う。範囲でしか持っていなければ使えない |
| 4 | **オプトアウト** | 広告の最適化を無効にする設定を用意し、プライバシーポリシーに導線を書く | — |
| 5 | **外向き表現に「収入」「所得」を使わない** | 内部区分としてのみ扱う。利用者に見える言葉は「あなたに合った」に統一 | 「あなたは低所得者向けセグメントです」と読める表示が 1 つ出れば、それで終わる |

### 制約 4 の順序（重要）

オプトアウトは**実装が先、ポリシー記載が後**。無い機能をポリシーに書くと、それ自体が虚偽記載になる。
現時点では未実装なので、公開ポリシーにも書いていない。
`test/lib/legal-documents.test.ts` の「実装していない約束を書かない」がこの順序を見張っている。

実装するときは 2 つを同じコミットに入れること:
1. 設定（`account_app_settings` 配下を想定）とその UI
2. `src/lib/legal/documents.ts` への導線の追記

### 制約 5 の適用範囲

利用者に見える文言すべて。**AI の system prompt も含む**（`src/app/api/ai/*`）。
AI に「この人は高所得層です」と書いた文脈を渡せば、生成文にその語彙が漏れる。

| ✗ 使わない | ✓ 使う |
|---|---|
| 収入に応じた広告 | あなたに合った情報 |
| 所得層別 | おすすめ |
| 高所得者向け / 低所得者向け | （表示しない。内部区分のみ） |

## 判断待ち（ユーザー）

- **最小セグメントサイズ N の値**。推奨は 100。小さくするほど広告主にとって価値が上がり、
  個人が特定される危険も上がる。**この数字は後から下げられない**（一度 N=10 で配ったデータは戻せない）。

## 実装するときの入口

- 既存の売上データ: `shop_shops/{shopId}/sales`、`personal_sales/{uid}/items`
  （**出所で当店分に絞る判定は `src/lib/shop-scope.ts` に一本化済み**。
  セグメント集計もこの判定を通すこと。掛け持ちキャストの他店売上を混ぜない）
- 集計の粒度は `ai/insights-narrative` が既に「セグメント集計＋サンプル名」の形を持っている
- 課金・広告の器は NOXA に 1 つ（`_design-source/NOXA-OS-ARCHITECTURE.md` の課金設計を参照）
